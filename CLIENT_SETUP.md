# Launch an independent client store

1. Copy `profiles/default.json` to a new public configuration file. Set a unique `storeId`, business name, approved contact details, layout, theme, policies and categories. Do not put credentials in JSON. Bank account details are public payment instructions, not authentication secrets; verify them with the client.
2. Run `scripts/new_client.py --config <file> --output <new-directory>`. It refuses existing destinations and excludes source secrets/data/Git history. The new project uses its own `profiles/default.json`. Create a new Git repository for it. Do not reuse Lola's Luxe's production repository or database.
3. Provision an independent Neon/PostgreSQL project with its own credentials. `DATABASE_SCHEMA=growthly_private` is private by default. Use the intended SSL connection string, least-privilege platform access and managed backups. Never reuse another client's DATABASE_URL. Keep DB credentials server-only.
4. Provision a client-owned Cloudinary account (all three credentials required), or a separate Supabase project with its own bucket/service key. Configure upload permissions and account ownership. A folder name alone is not a secure account boundary.
5. Generate a fresh session secret using `python -c 'import secrets; print(secrets.token_hex(32))'`, enter it privately in the host, and keep it out of Git/chat. Set `APP_ENV=production`, `PREVIEW=0`, `COOKIE_SECURE=1`, `SITE_URL=https://client-domain`, `STORE_CONFIG_PATH=profiles/default.json`, `STORE_ID=<unique-id>`, database and storage variables. Process environment variables must actually be exported; copying `.env.example` does not load it.
6. Enable only approved fulfilment/payment options. WhatsApp requires an international digits-only number. Bank transfer requires confirmed bank details and a human verification procedure. Paystack requires `PAYSTACK_SECRET_KEY` (first in test mode), `onlinePayment=true`, and webhook `https://client-domain/api/gateway/webhook`. Test provider initialization, server verification, wrong amount/currency, callback, webhook, retries and reconciliation. Never expose the key in public configuration.
7. From a trusted terminal securely connected to that client's database, run `python app.py owner-invite --username owner --site-url https://client-domain`. Send the single-use setup link privately to the owner. It expires after 24 hours. The owner sets her/his own password, signs in at `/admin`, and invites Product Admins from Team. No public signup is enabled. The `owner` command remains an operator recovery option.
8. Replace demonstration products with verified client images, prices, variants and stock. Demo seeding requires PREVIEW; seeded products cannot be sold/displayed in production. Do not change demonstrations into purported real products without checking imagery and all details. Product Admins save drafts; the owner publishes approved products.
9. Complete approved About, contact, privacy, delivery, returns and warranty information. Draft policies are placeholders, not legal advice or launch-ready policy text. Provide a real hero/logo if desired, and test keyboard navigation, zoom, mobile, empty/error states and image loading.
10. Run backend/browser checks in an isolated staging database; never run test fixtures against production. Run a real staging order, manual receipt and provider sandbox payment with the owner. Confirm stock and analytics, staff restrictions, owner recovery, data isolation and backup recovery.
11. Review the Vercel project and environment variables. Deploy only after explicit approval; connect the client's domain/DNS and verify HTTPS. For a conventional Python host, run `gunicorn app:app` with production environment variables and TLS at the ingress. The `vercel.json` packages Flask/templates/static with the Python builder; no Node build is needed. A live build/domain/provider deployment has not been performed in this workspace.
12. Hand over client-owned account access, the private admin URL, instructions, backup/monitoring responsibility and ongoing support terms. Keep agency maintenance access explicit and revocable; do not share the owner's password.

## Local convenience

For SK Plug, the example has real location names but no invented phone/email/bank account. Configure these from client-approved information. Use a separate DATA_DIR for every local store (required if running two development apps); the production database requirement prevents SQLite fallback on serverless hosts.

## Upgrade policy

Review core changes against the starter's tests; port them into each independent client repository as a reviewed change. Do not overwrite a client's frontend/profile/data. This repository is a template, not a shared runtime package or multi-tenant service. Maintain a version/changelog and validate each client before release.
